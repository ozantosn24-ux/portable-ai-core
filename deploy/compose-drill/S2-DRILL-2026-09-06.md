# Identity drill (OIDC + resource authorization) — 2026-09-06

One recorded run of `deploy/compose-drill` with the `idp` profile: Keycloak pull, bring-up,
realm import, three end-to-end logins driven by curl, authorization checks, and the
authorization ledger read out of the container. **Every number below is copied from that
run's output.** Where something failed, the failure and its exact error are kept — three of
the four most useful findings here are failures.

**Environment.** GitHub Codespace, Ubuntu (kernel 6.8.0-1052-azure), **2 vCPU / 7.757 GiB
RAM / 32 GB overlay filesystem**, Docker **29.7.2**, Docker Compose **v2.40.3**. An
unrelated container (`wozto-control-plane`, a Kubernetes node from an older lab) ran
throughout and held **1.021 GiB** of RAM; it was left running. Shared, virtualised host —
treat every timing as an order of magnitude, not a capacity model.

**Scope.** Only `postgres`, `keycloak` and `app` were started. `n8n`, `n8n-runner` and
`caddy` are not part of this drill; starting them would spend ~1 GB of RAM re-proving what
[`DRILL-2026-09-06.md`](DRILL-2026-09-06.md) already recorded.

⇒ The Keycloak issuer shape `<base>/realms/<realm>` is **confirmed by measurement**, and

JWKS carries **two** keys: one `RS256` (signature) and one `RSA-OAEP` (encryption). That is

## 7. Failures — the useful part

Four things broke. All four are now fixed in the committed files, and each fix carries its
error message where it happened.

**(a) Keycloak ignores `*_FILE` secrets — unlike every other service in this stack.**
`KC_BOOTSTRAP_ADMIN_PASSWORD_FILE` produced a crash loop:

```
bootstrap-admin-username available only when bootstrap admin password is set
```

and after that was worked around, `KC_DB_PASSWORD_FILE` failed differently:

```
org.postgresql.util.PSQLException: The server requested SCRAM-based authentication,
but no password was provided.
```

Fix: `idp/keycloak-entrypoint.sh` maps `KC_<OPTION>_FILE` → `KC_<OPTION>`.

⚠️ **A wrong reading nearly shipped here.** `kc.sh show-config` prints
`kc.db-password-file = ******* (ENV)`, which looks like the option was honoured. It was
not — show-config echoes the key, it does not prove the option is used. The proof was the
connection attempt. *One hit is not a classification.*

**(b) A named volume is `root:root`, and the app runs as uid 10001.**

```
PermissionError: [Errno 13] Permission denied: '/drill-ledger/decisions.jsonl'
```

Fix: create `/drill-ledger` in the image owned by 10001 so Docker propagates that ownership
to the fresh volume. Same class as the n8n `/home/node/.cache` mode problem already recorded
in `compose.yaml` — a mount point's ownership is an image concern.

⭐ **The failure was fail-closed.** `authorize()` writes the ledger row *before* returning a
decision, so an unwritable ledger produced a **500, never an unlogged allow**. That ordering
is load-bearing and worth keeping.

**(c) Keycloak's `VERIFY_PROFILE` required action hijacked the login.** With users that had
no `email`, the login-form POST redirected to
`/login-actions/required-action?execution=VERIFY_PROFILE` instead of back to the RP. Fix:
give the drill users an email and disable the action in the realm import.

**(d) Realm roles are not in the ID token by default.** The first successful login returned
`"roles":[]` even though alice holds `mailbox-user`: Keycloak's built-in realm-role mapper
targets the **access** token. Fix: an explicit `oidc-usermodel-realm-role-mapper` on the
`drill-app` client with `id.token.claim: true` and `claim.name: realm_access.roles`.

⇒ Note the security shape here: with roles empty, authorization still behaved correctly,
because **roles do not grant mailbox access — the grant table does**. The bug was cosmetic
precisely because the two layers are separate.

## 8. Secret handling — measured, and one claim corrected

| Where | Bootstrap admin / DB password |
|---|---|
| `docker inspect .Config.Env` (keycloak) | only `KC_BOOTSTRAP_ADMIN_PASSWORD_FILE=` / `KC_DB_PASSWORD_FILE=` paths |
| `docker inspect .Config.Env` (app) | only `WOZTO_REFERENCE_SESSION_SECRET_FILE=` / `DRILL_DB_PASSWORD_FILE=` paths |
| `docker exec <c> env` | **not present** (grep count 0) |
| `/proc/1/environ` | **present** (grep count 2) |

⚠️ The middle row corrects a claim that was written before it was measured. `docker exec`
starts a new process from the image/Compose environment and does **not** inherit what the
entrypoint exported. The real exposure is PID 1's environment. File secrets keep the value
out of the image, out of `compose.yaml` and out of `docker inspect`; they do **not** keep it
out of the process environment once a shim exports it. The trade-off is recorded as
[ADR 0009](../../docs/adr/0009-keycloak-file-secret-exception.md), amending ADR 0005.

**Two further exposure vectors, named rather than left implicit:**

* **`/proc/<pid>/cmdline` during database init.** `initdb/20-drill-keycloak-db.sh` first
  passed the new role's password to `psql` as `-v kc_password=…`. Command-line arguments are
  world-readable inside the container, so any process running during the init window could
  read it. It now uses `\getenv` (psql 16+), so the value travels in the environment, which
  is readable only by the same user. ⚠️ **The sibling `10-drill-n8n-db.sh` still uses the
  `-v` form.** It was left alone deliberately — it belongs to the base drill, not this
  change — and is named here so it is a known open item, not an oversight.
* **`sslRequired: "none"` in the realm.** `idp/realm-drill.json` disables Keycloak's TLS
  requirement. That is what makes a plain-HTTP drill possible at all, and it is
  **drill-only**: a realm serving real users with `none` accepts credentials in cleartext.
  A real deployment restores `external` (the Keycloak default) and terminates TLS.

## 9. What this drill does NOT prove

* **`start-dev`.** Keycloak ran in development mode — no production hostname checks, no TLS,
  dev-grade caching. This drill proves the OIDC *protocol* path, not a hardened IdP.
* **No TLS in front of the IdP or the app.** Both were published on loopback over plain
  HTTP, so the session cookie ran with `Secure=0`. TLS is proven in the earlier drill; it
  was not re-proven here, and Caddy was deliberately left out (see the header of
  `compose.idp.yaml` for why).
* **One image layer is not hash-verified.** The base app image installs from
  `requirements.lock` with `--require-hashes`; `joserfc` is not in that lock (measured:
  `httpx==0.28.1` *is*), so `idp/Dockerfile.app-auth` adds exactly one package without hash
  verification. Closing it means regenerating the lock with the extra.
* **No load, no concurrency, no soak.** Three sequential logins. Nothing here says anything
  about behaviour under concurrent sessions, JWKS-fetch storms, or memory pressure.
* **No token refresh, no back-channel logout, no MFA, no Conditional Access.** None are
  implemented, so none were measured.
* **No Entra ID.** `docs/identity-entra-migration.md` is a reading of documentation. No
  Microsoft tenant was contacted at any point.
* **Single node, synthetic data.** One Postgres, no replication. The users, mailboxes, roles
  and passwords are fixtures; the realm passwords are literally
  `drill-not-a-real-password-<user>`.
* **Cold-build timings are absent.** The recorded build numbers are warm-cache; only the
  Keycloak pull has a genuine cold measurement (16.7 s).
* **A Codespace is not a VPS.** Overlay filesystem, shared host, an unrelated 1 GiB
  container alongside.

## 11. Post-handover-drill fixes — 2026-09-07

A context-free engineer ran this stack from the README alone
(`DEVIR-PROVASI-2026-09-06.md`): base stack 6/6 first try, then `scripts/idp_up.sh` burned
its full 900 s ceiling and failed with `dependency failed to start: container
drill-postgres-1 is unhealthy`. Every number below was re-measured in the same Codespace
while fixing it (`deploy-lab-q7w9xvr7rwqwh64wv`, Docker 29.7.2, Compose v2.40.3).

**§2 above never exercised the bug, and that is the lesson.** §2 records a bring-up "from
`down -v` (no containers, no volumes)" — the profile created the volume itself, so
`initdb/*` ran with the Keycloak secret mounted. The README's own order does the opposite.
*A drill that only ever runs its own happy path measures the happy path.*

### (a) The Keycloak role was never created — and the base stack could not create it

`initdb/*` runs once, on an empty `PGDATA`. Worse, `initdb/20-drill-keycloak-db.sh` is
mounted into the **base** stack too, where the `keycloak_db_password` secret is not. So a
base-only `scripts/up.sh` on a genuinely fresh volume does this, every time:

```
/usr/local/bin/docker-entrypoint.sh: sourcing /docker-entrypoint-initdb.d/20-drill-keycloak-db.sh
cat: /run/secrets/keycloak_db_password: No such file or directory

PostgreSQL Database directory appears to contain a database; Skipping initialization
```

Initialisation aborts, the container dies, `restart: unless-stopped` brings it back, the
second boot finds a non-empty `PGDATA` and skips init — and the stack reports **all six
services healthy**, because the base healthcheck only asserts the `drill_n8n` role that the
earlier `10-` script did create. Measured every time: `RestartCount=1`, and
`select count(*) from pg_roles where rolname = 'drill_keycloak'` → **0**.

⚠️ **It is also a race, not a deterministic self-heal.** Four fresh base bring-ups: three
went healthy (the restart beat Compose's dependency wait), one lost and failed outright
with `dependency failed to start: container drill-postgres-1 is unhealthy` — the base
stack's own README path, failing for a reason the README does not mention.

**Fix 1 — the consequence.** `scripts/idp_up.sh` creates the role and database itself,
idempotently (`\gexec` guarded by `pg_roles` / `pg_database`), before starting the profile,
and reads them back from the server. The password still never touches argv: it is the first
line of stdin, exported inside the container, picked up with `\getenv` — the same rule as
`initdb/20-drill-keycloak-db.sh`. **The SQL is not duplicated:** the script parses the
statements out of that init script and refuses to run if they no longer match the idempotent
form it mirrors.

**Fix 2 — the cause.** `20-drill-keycloak-db.sh` was treating a missing secret as a fatal
error inside a stack that is not supposed to have one. It now skips, and says so:

```
initdb: keycloak secret not mounted; idp role/db will be ensured by scripts/idp_up.sh
```

⚠️ Guarded with an `if`, deliberately **not** an early `exit 0`. The official entrypoint
*sources* a non-executable init file (`docker-entrypoint.sh: sourcing …` — and this file is
committed 644, see (c), so that is the path actually taken), and in a sourced file `exit`
terminates the **entrypoint itself**, half-way through initialisation. An `exit 0` here
would have replaced a loud failure with a silent one.

**Proof — three consecutive fresh base-only bring-ups, `down -v` between each:**

| | run 1 | run 2 | run 3 |
|---|---:|---:|---:|
| `up.sh` exit code | 0 | 0 | 0 |
| `ALL_HEALTHY_SECONDS` | **40.1** | **39.9** | **35.1** |
| postgres `RestartCount` | **0** | **0** | **0** |
| `[1] LOG: database system is ready…` | **1** | **1** | **1** |
| `No such file or directory` in the log | **0** | **0** | **0** |
| skip line present | 1 | 1 | 1 |
| `drill_n8n` role (the base healthcheck) | 1 | 1 | 1 |
| `drill_keycloak` role | 0 | 0 | 0 |

⚠️ The count of *all* "ready to accept connections" lines is **2**, not 1, on a clean first
boot — the official entrypoint runs a temporary server during `initdb` and that server logs
the line too. The line that distinguishes a restart is the **PID 1** one, and it appears
exactly once. Counting the unqualified string would have called a healthy boot a restart.

### (b) Failure took 900 s to surface

The old loop watched health only. Compose had already given up, but nothing read its exit
code. The exit code is now the primary signal and `DRILL_UP_TIMEOUT` is a backstop.

**`scripts/up.sh` carried the identical bug, and it fired during this work** — when the
race in (a) went the wrong way, Compose failed at ~10 s and `up.sh` spun toward its own
900 s ceiling with every other service stuck at `Created`. It now uses the same pattern.
Negative control (base healthcheck pointed at a role that does not exist):

| | |
|---|---:|
| `up.sh` exit code | **1** |
| Wall clock | **66.2 s** — Compose's own 12 × 5 s healthcheck budget |
| **Compose failing → script exiting** | **2.43 s** (was: 900 s) |
| Printed | `UP_FAILED after 64.6s: docker compose up exited with status 1`, the Compose output ending in `dependency failed to start: container drill-postgres-1 is unhealthy`, the `ps` table (four services `Created`), and postgres's last 20 log lines |

`compose.yaml` restored byte-identical afterwards; the positive control that followed came
up in **34.8 s**, exit 0, `RestartCount=0`.

⚠️ Writing the sentinel needed an explicit `set +e` in the subshell — without it errexit
killed the subshell before it could record the code, and the symptom was *identical to the
bug being fixed*. Caught only because the fix was run against a real failure.

### (c) Keycloak could never have started from a fresh clone

Not reachable in the handover drill, because it failed earlier. `idp/keycloak-entrypoint.sh`
is committed with mode **644**, and a bind-mounted file keeps the host checkout's mode:

```
OCI runtime create failed: runc create failed: unable to start container process:
error during container init: exec: "/drill-idp/keycloak-entrypoint.sh": permission denied
```

Fixed structurally in `compose.idp.yaml` — `entrypoint: ["/bin/bash", "…"]` — so it does
not depend on host filesystem state. (`/bin/bash` 5.1.8 is present in `keycloak:26.7.3`;
verified.) The same mode problem hits `scripts/*.sh`, which a fresh clone cannot execute at
all; the README now opens with `chmod +x scripts/*.sh`. **Not fixed here:** the file modes
in git. That needs `git update-index --chmod=+x`, which is a repository change, not a
drill change.

### (d) The bring-up loop was reporting the containers it was about to lose

Adding the profile to a running stack makes Compose **recreate** postgres and app. The loop
marked the *old* containers healthy and never looked again — visibly, in the handover
drill's own failure output, `postgres healthy at +0.2s` sits one line above
`postgres = unhealthy`. Measured here before the fix: `ALL_HEALTHY_SECONDS=87.3` printed
while `drill-app-1` was 1 second old and still `health: starting`. **A green number from a
container that no longer exists.** The loop now carries the container id with the timing,
re-measures when the id changes, and will not exit until Compose itself has finished.

### (f) Keycloak survives a Postgres replacement as a *healthy* container that cannot log anyone in

Found while recovering from the negative control, and the most useful finding of the second
round. `idp_up.sh` returned 0 and every container was healthy — and `idp_check.sh alice`
still failed at `unexpected callback URL: <empty>`, because Keycloak's pool was holding
handles to a Postgres container that no longer exists:

```
Caused by: org.postgresql.util.PSQLException: This connection has been closed.
WARN [io.agroal.pool] Datasource '<default>': This connection has been closed.
```

⭐ **Six healthy containers and a zero exit code did not mean the system worked.** Keycloak's
readiness probe answers on the management port and never touches the database, so it cannot
see this. Only the end-to-end check caught it — which is the whole argument for having
`idp_check.sh` at all, and the reason a bring-up script's exit code is not a verdict.

**Fixed:** `idp_up.sh` now compares the postgres container id across its own bring-up; if
Postgres was replaced while Keycloak was not, it restarts Keycloak and waits for health
again before reporting success. Verified by reproducing the state deliberately — Postgres
put back on the base config under a live Keycloak, then `idp_up.sh`:

```
keycloak: postgres was replaced underneath it; restarting to drop dead JDBC handles
KEYCLOAK_RESTART_SECONDS=18.0
```

after which `idp_check.sh alice` passed **with no manual step**.

**Residual, recorded as TD-077:** any other route into the same state is still invisible,
because the probe still does not exercise a DB round-trip. Closing that means a healthcheck
that performs one.
