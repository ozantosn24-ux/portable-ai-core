# Identity drill (OIDC + resource authorization) — 2026-09-06

One recorded run of `deploy/compose-drill` with the `idp` profile: Keycloak pull, bring-up,
realm import, three end-to-end logins driven by curl, authorization checks, and the
authorization ledger read out of the container. **Every number below is copied from that
run's output.** Where something failed, the failure and its exact error are kept — three of
the four most useful findings here are failures.

**Environment.** GitHub Codespace, Ubuntu (kernel 6.8.0-1052-azure), **2 vCPU / 7.757 GiB
RAM / 32 GB overlay filesystem**, Docker **29.7.2**, Docker Compose **v2.40.3**. An
unrelated container (`wozto-control-plane`, a Kubernetes node from an older lab) ran
throughout and held **1.021 GiB** of RAM; it was left running. Shared, virtualised host —
treat every timing as an order of magnitude, not a capacity model.

**Scope.** Only `postgres`, `keycloak` and `app` were started. `n8n`, `n8n-runner` and
`caddy` are not part of this drill; starting them would spend ~1 GB of RAM re-proving what
[`DRILL-2026-09-06.md`](DRILL-2026-09-06.md) already recorded.

```

authorization_endpoint <issuer>/protocol/openid-connect/auth
token_endpoint         <issuer>/protocol/openid-connect/token
userinfo_endpoint      <issuer>/protocol/openid-connect/userinfo

code_challenge_methods_supported        ["plain","S256"]
token_endpoint_auth_methods_supported   ["private_key_jwt","client_secret_basic",
                                         "client_secret_post","tls_client_auth",
                                         "client_secret_jwt"]
```

⇒ The Keycloak issuer shape `<base>/realms/<realm>` is **confirmed by measurement**, and
`docs/identity-entra-migration.md` cites this run rather than a docs page for it.

JWKS carries **two** keys: one `RS256` (signature) and one `RSA-OAEP` (encryption). That is
not a curiosity — it is why `_lookup_key` refuses to guess when a token omits `kid` and the
key set holds more than one key.

## 4. End-to-end logins (curl-driven, full redirect chain)

`scripts/idp_check.sh <user>` follows `/auth/login` → Keycloak → login-form POST →
`/auth/callback` → `/me`. Nothing is called directly, so a wrong `Location` fails here.

**alice** (`sub` `1111…1111`, realm role `mailbox-user`, grant `sales-a: owner`):

| Assertion | Result |
|---|---|
| authorize URL points at the realm | PASS |
| `code_challenge_method=S256` present | PASS |
| IdP redirected back with an authorization code | PASS |
| `/auth/callback` | **303** |
| `/me` → `roles:["mailbox-user"]`, `grants:[{sales-a, owner}]` | PASS |
| `GET /mailboxes/sales-a/summary` | **200** |
| `GET /mailboxes/sales-b/summary` | **403** |
| `POST /mailboxes/sales-a/drafts` (with CSRF) | **201** |
| `POST /mailboxes/sales-a/drafts` (no CSRF) | **403** |
| `POST /auth/logout` (with CSRF) | **204** |
| `GET /me` after logout (same cookie) | **401** |

**bob** (`sub` `2222…2222`, grant `sales-b: owner`): `sales-b` summary **200**, `sales-a`
summary **403**, logout 204, `/me` after logout 401. ALL CHECKS PASSED.

**mia** (`sub` `3333…3333`, realm role `mailbox-manager`, `manager_view` on both):
`sales-a` summary **200**, `sales-b` summary **200**, `POST .../drafts` **403**
(`role_forbids_action`), logout 204, `/me` after logout 401. ALL CHECKS PASSED.

⭐ **`roles` arrived through the configured claim path.** `/me` shows
`roles:["mailbox-user"]` / `["mailbox-manager"]`, read from `realm_access.roles` — the
`roles_claim_path` config is exercised against a real IdP, not only against the test double.

|--:|---|---|---|---|---|---|
| 1 | alice | view_summary | sales-a | `sales-a` | allow | grant_permits_action |
| 2 | alice | view_summary | sales-b | **`null`** | deny | no_grant_for_mailbox |
| 3 | alice | draft | sales-a | `sales-a` | allow | grant_permits_action |
| 4 | bob | view_summary | sales-b | `sales-b` | allow | grant_permits_action |
| 5 | bob | view_summary | sales-a | **`null`** | deny | no_grant_for_mailbox |
| 6 | mia | view_summary | sales-a | `sales-a` | allow | grant_permits_action |
| 7 | mia | view_summary | sales-b | `sales-b` | allow | grant_permits_action |
| 8 | mia | draft | sales-a | `sales-a` | deny | role_forbids_action |

Three things this table proves that a status code alone would not:

* **`mailbox_id` is `null` on every `no_grant` deny**, while `requested_mailbox_id` carries
  what was asked for. The target was never taken from request input; the request value only
  ever became a lookup key.
* **The CSRF-less draft attempt produced NO row.** CSRF is checked before authorization, so
  an unevaluated request does not become a decision. 8 rows, not 9.
* `tr -cd '\r' | wc -c` → **0**. LF-only lines, as `jsonl_ledger` intends.

## 7. Failures — the useful part

Four things broke. All four are now fixed in the committed files, and each fix carries its
error message where it happened.

**(a) Keycloak ignores `*_FILE` secrets — unlike every other service in this stack.**
`KC_BOOTSTRAP_ADMIN_PASSWORD_FILE` produced a crash loop:

```
bootstrap-admin-username available only when bootstrap admin password is set
```

and after that was worked around, `KC_DB_PASSWORD_FILE` failed differently:

```
org.postgresql.util.PSQLException: The server requested SCRAM-based authentication,
but no password was provided.
```

Fix: `idp/keycloak-entrypoint.sh` maps `KC_<OPTION>_FILE` → `KC_<OPTION>`.

⚠️ **A wrong reading nearly shipped here.** `kc.sh show-config` prints
`kc.db-password-file = ******* (ENV)`, which looks like the option was honoured. It was
not — show-config echoes the key, it does not prove the option is used. The proof was the
connection attempt. *One hit is not a classification.*

**(b) A named volume is `root:root`, and the app runs as uid 10001.**

```
PermissionError: [Errno 13] Permission denied: '/drill-ledger/decisions.jsonl'
```

Fix: create `/drill-ledger` in the image owned by 10001 so Docker propagates that ownership
to the fresh volume. Same class as the n8n `/home/node/.cache` mode problem already recorded
in `compose.yaml` — a mount point's ownership is an image concern.

⭐ **The failure was fail-closed.** `authorize()` writes the ledger row *before* returning a
decision, so an unwritable ledger produced a **500, never an unlogged allow**. That ordering
is load-bearing and worth keeping.

**(c) Keycloak's `VERIFY_PROFILE` required action hijacked the login.** With users that had
no `email`, the login-form POST redirected to
`/login-actions/required-action?execution=VERIFY_PROFILE` instead of back to the RP. Fix:
give the drill users an email and disable the action in the realm import.

**(d) Realm roles are not in the ID token by default.** The first successful login returned
`"roles":[]` even though alice holds `mailbox-user`: Keycloak's built-in realm-role mapper
targets the **access** token. Fix: an explicit `oidc-usermodel-realm-role-mapper` on the
`drill-app` client with `id.token.claim: true` and `claim.name: realm_access.roles`.

⇒ Note the security shape here: with roles empty, authorization still behaved correctly,
because **roles do not grant mailbox access — the grant table does**. The bug was cosmetic
precisely because the two layers are separate.

## 8. Secret handling — measured, and one claim corrected

| Where | Bootstrap admin / DB password |
|---|---|
| `docker inspect .Config.Env` (keycloak) | only `KC_BOOTSTRAP_ADMIN_PASSWORD_FILE=` / `KC_DB_PASSWORD_FILE=` paths |
| `docker inspect .Config.Env` (app) | only `WOZTO_REFERENCE_SESSION_SECRET_FILE=` / `DRILL_DB_PASSWORD_FILE=` paths |
| `docker exec <c> env` | **not present** (grep count 0) |
| `/proc/1/environ` | **present** (grep count 2) |

⚠️ The middle row corrects a claim that was written before it was measured. `docker exec`
starts a new process from the image/Compose environment and does **not** inherit what the
entrypoint exported. The real exposure is PID 1's environment. File secrets keep the value
out of the image, out of `compose.yaml` and out of `docker inspect`; they do **not** keep it
out of the process environment once a shim exports it. The trade-off is recorded as
[ADR 0009](../../docs/adr/0009-keycloak-file-secret-exception.md), amending ADR 0005.

**Two further exposure vectors, named rather than left implicit:**

* **`/proc/<pid>/cmdline` during database init.** `initdb/20-drill-keycloak-db.sh` first
  passed the new role's password to `psql` as `-v kc_password=…`. Command-line arguments are
  world-readable inside the container, so any process running during the init window could
  read it. It now uses `\getenv` (psql 16+), so the value travels in the environment, which
  is readable only by the same user. ⚠️ **The sibling `10-drill-n8n-db.sh` still uses the
  `-v` form.** It was left alone deliberately — it belongs to the base drill, not this
  change — and is named here so it is a known open item, not an oversight.
* **`sslRequired: "none"` in the realm.** `idp/realm-drill.json` disables Keycloak's TLS
  requirement. That is what makes a plain-HTTP drill possible at all, and it is
  **drill-only**: a realm serving real users with `none` accepts credentials in cleartext.
  A real deployment restores `external` (the Keycloak default) and terminates TLS.

## 9. What this drill does NOT prove

* **`start-dev`.** Keycloak ran in development mode — no production hostname checks, no TLS,
  dev-grade caching. This drill proves the OIDC *protocol* path, not a hardened IdP.
* **No TLS in front of the IdP or the app.** Both were published on loopback over plain
  HTTP, so the session cookie ran with `Secure=0`. TLS is proven in the earlier drill; it
  was not re-proven here, and Caddy was deliberately left out (see the header of
  `compose.idp.yaml` for why).
* **One image layer is not hash-verified.** The base app image installs from
  `requirements.lock` with `--require-hashes`; `joserfc` is not in that lock (measured:
  `httpx==0.28.1` *is*), so `idp/Dockerfile.app-auth` adds exactly one package without hash
  verification. Closing it means regenerating the lock with the extra.
* **No load, no concurrency, no soak.** Three sequential logins. Nothing here says anything
  about behaviour under concurrent sessions, JWKS-fetch storms, or memory pressure.
* **No token refresh, no back-channel logout, no MFA, no Conditional Access.** None are
  implemented, so none were measured.
* **No Entra ID.** `docs/identity-entra-migration.md` is a reading of documentation. No
  Microsoft tenant was contacted at any point.
* **Single node, synthetic data.** One Postgres, no replication. The users, mailboxes, roles
  and passwords are fixtures; the realm passwords are literally
  `drill-not-a-real-password-<user>`.
* **Cold-build timings are absent.** The recorded build numbers are warm-cache; only the
  Keycloak pull has a genuine cold measurement (16.7 s).
* **A Codespace is not a VPS.** Overlay filesystem, shared host, an unrelated 1 GiB
  container alongside.

## 10. Cleanup

```bash
docker compose -p drill -f compose.yaml -f compose.idp.yaml --profile idp down -v
rm -f secrets/keycloak_db_password.txt secrets/keycloak_admin_password.txt secrets/session_secret.txt

# scripts/idp_up.sh appends two host entries so the issuer resolves to the same URL from
# the host and from inside the network. They outlive `down -v`, so remove them explicitly:
sudo sed -i '/^127\.0\.0\.1[[:space:]]\+idp\.drill\.internal$/d' /etc/hosts
sudo sed -i '/^127\.0\.0\.1[[:space:]]\+app\.drill\.internal$/d' /etc/hosts
```

Scripts and configuration are kept; generated secrets and volumes are not. The pre-existing
`wozto-control-plane` container was never touched.

⚠️ In the recorded run the two `/etc/hosts` lines were **left in place** — they are
harmless loopback entries, but they are host state this drill created, so they are listed
here rather than quietly forgotten.
