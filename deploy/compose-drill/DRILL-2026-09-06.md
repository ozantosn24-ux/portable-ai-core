# Deployment drill — 2026-09-06

One recorded run of `deploy/compose-drill` end to end: pull, build, up, seed, TLS check,
backup, restore, verify. **Every number below is copied from that run's output.** Where a
step failed, the failure and its exact error are kept rather than smoothed over — the
failures are the most useful part of the record.

**Environment.** GitHub Codespace, Ubuntu 24.04, 2 vCPU / 7.76 GiB RAM / 32 GB overlay
filesystem, Docker 29.7.2, Docker Compose v2.40.3. An unrelated container (a Kubernetes
node from an older lab) was running throughout and held ~0.99 GiB of RAM; it was left
running. This is a shared, virtualised host — treat every timing as an order of
magnitude, not as a capacity model.

## 3. n8n workflow readiness

Readiness is measured as *the production webhook returns 200*, not as *the port is open*.

| Step | |
|---|---:|
| `import:workflow` + `publish:workflow` | 10.2 s |
| Webhook still `404` after | 19.6 s |
| n8n restart required | **yes** |
| First `200` from `https://n8n.drill.internal:18443/webhook/drill-ping` | **32.1 s** |

`publish:workflow` exists in 2.36.7 (`update:workflow` is marked `[DEPRECATED] - use
publish:workflow or unpublish:workflow instead`) and it says so itself when the running
instance will not see the change:

```
Publishing workflow with ID: drillping0000001 (current version)
Note: Changes will not take effect if n8n is running.
Please restart n8n for changes to take effect if n8n is currently running.
```

So a CLI publish against a live instance is a two-step operation. Anything that publishes
workflows from a pipeline has to restart n8n (or use the editor) and then *poll the
webhook*, because until that restart the endpoint answers 404 while every healthcheck is
green.

## 6. Findings — the four ways this stack broke before it worked

### 6.1 Compose ignores `uid`/`gid`/`mode` on file secrets

Outside swarm mode, a Compose file secret is bind-mounted with the **host** file's owner
and permissions. Compose v2.40.3 says so explicitly:

```
level=warning msg="secrets `uid`, `gid` and `mode` are not supported, they will be ignored"
```

Measured with a probe container running as uid 10001 against a 0600 host file: the mount
appears as `-rw------- 1 1000 1000` and reading it returns `Permission denied`.

The container users are all different — postgres 999, n8n and the runner 1000, the app
image 10001 — so 0600 secrets owned by the deploy user break most of them. First run of
this drill died exactly there: `cat: /run/secrets/n8n_db_password: Permission denied`.
Fix: the `secrets/` directory is 0700 and the files inside are 0644.

### 6.2 A healthy Postgres that was never initialised

The consequence of 6.1 was worse than a clear failure. The init script that creates n8n's
role died on the unreadable secret, the entrypoint aborted, `restart: unless-stopped`
restarted the container, and the **second** boot found a non-empty `PGDATA` and skipped
initialisation entirely. `pg_isready` then reported the server healthy — with the n8n role
missing and n8n crash-looping on `password authentication failed for user "drill_n8n"`.

Evidence: `RestartCount=1`, and `database system is ready to accept connections` logged
twice.

The healthcheck now asserts that the object the init script was supposed to create exists,
so a half-initialised database can never report healthy:

```yaml
pg_isready -U drill_app -d drill_app && psql -U drill_app -d drill_app -tAc
  "SELECT count(*) FROM pg_roles WHERE rolname = 'drill_n8n'" | grep -qx 1
```

### 6.3 `read_only` for n8n, and a false positive that hid the failure

A short-syntax `tmpfs:` entry inherits the mode of the directory that already exists in
the image. `/tmp` exists as `1777` and is writable; `/home/node/.cache` does **not** exist,
so Compose creates the mountpoint as `mode=755 owner=root:root` and n8n (uid 1000) dies:

```
Error: EACCES: permission denied, mkdir '/home/node/.cache/n8n'
```

The fix is long-syntax tmpfs with an explicit `mode: 01777`, verified by
`stat -c %a` → `1777` inside the container.

The trap worth remembering is how this was nearly missed. **n8n answers
`/healthz/readiness` with 200 before it finishes generating static assets**, so the first
probe of this configuration was sampled at t+60 s, reported `health=healthy restarts=0`,
and was recorded as a success — the crash came afterwards. A later run caught it only
because the webhook started returning 502. Health at one instant is not stability; the
run now re-checks `RestartCount` 90 s after all-healthy.

### 6.4 A `pg_restore` that exits 0 and leaves the application unable to start

The first restore attempt used `--no-owner --no-privileges`. `pg_restore` exited 0 and all
129 n8n tables came back owned by the superuser `drill_app` instead of `drill_n8n`. n8n
connected as `drill_n8n`, failed its migrations on a relation it could not touch, and
crash-looped. Dropping those flags restores ownership from the dump, which works because
the init script re-creates the roles first. The restore now prints table ownership as part
of verification.

Related, same family: with `read_only: true` the daemon refuses `docker cp` **into** the
container at all — `Error response from daemon: container rootfs is marked read-only` —
even when the destination is a tmpfs path. Files the n8n CLI must read are mounted
read-only instead, and the workflow export comes back out as a `tar` stream.

## 7. Secrets — verified by observation, not by assumption

| Claim | Evidence |
|---|---|
| Postgres honours `POSTGRES_PASSWORD_FILE` | `POSTGRES_PASSWORD` in container env: **0** occurrences; `POSTGRES_PASSWORD_FILE`: 1; scram auth from the app succeeds and its schema exists |
| n8n honours `N8N_ENCRYPTION_KEY_FILE` | `N8N_ENCRYPTION_KEY` in container env: **0**; in `docker inspect .Config.Env`: **0**; sha256 of the key n8n persisted to `/home/node/.n8n/config` == sha256 of the secret file (`34cd451e…` both sides) |
| n8n honours `DB_POSTGRESDB_PASSWORD_FILE` | n8n connects and migrates with no password variable set; it also logs that it trimmed the file's trailing newline |
| The app never sees a password | `PGPASSWORD` in app env: **0**; the libpq passfile is `600 appuser:appuser` on a `tmpfs (rw,nosuid,nodev,noexec)` mount |
| Two databases are actually isolated | `has_database_privilege('drill_n8n','drill_app','CONNECT')` → **`f`** |
| Data checksums are on | `SHOW data_checksums` → **`on`** (an init-time-only choice) |

### The runner image *does* read `_FILE` — the docs say it does not

n8n's documentation states that the task-runner image cannot use file-based configuration
for secrets and that "variables with a `_FILE` suffix added will not be recognized".
Measured against `n8nio/runners:2.36.7`, three controls against the live broker:

| Case | Result |
|---|---|
| `N8N_RUNNERS_AUTH_TOKEN_FILE` + correct token | broker logs `Registered runner "launcher-javascript"` and `"launcher-python"` |
| `N8N_RUNNERS_AUTH_TOKEN_FILE` + **wrong** token | never registers; broker logs nothing for 20 s |
| no token variable at all | launcher refuses to start: `Failed to load config: AuthToken: missing required value: N8N_RUNNERS_AUTH_TOKEN` |
| `N8N_RUNNERS_AUTH_TOKEN` plain env, correct token (positive control) | registers |

The only difference between rows 1 and 2 is the *contents* of the file, and row 3 proves
the variable is mandatory. So the file is read. The stack therefore uses `_FILE` on the
runner too, and keeps no plaintext `.env` copy of the token. If a future version stops
reading it, row 3 shows the failure is loud at startup rather than silent — but re-run
these three controls after a version bump rather than trusting this line.

## 10. Day-1 checklist, mapped to what was measured

| Day-1 item | Where it is done | What the drill showed |
|---|---|---|
| Compose with pinned images | `compose.yaml` | All five tags `docker pull`-verified; one plausible tag (`docker.n8n.io/n8nio/runners`) does not exist — verify, do not guess (§1). |
| External task runners | `n8n` + `n8n-runner`, port 5679, `N8N_RUNNERS_BROKER_LISTEN_ADDRESS=0.0.0.0` | Both launchers register against the broker; token supplied by file, proven by wrong-token and no-token controls (§7). |
| Encryption key generated up front, backed up separately from the database | `scripts/gen_secrets.sh`, `scripts/backup.sh` | Key file hash matches what n8n persisted (§7); the restore decrypts a credential using only the key backup (§5). |
| Execution retention decided before the disk fills | `EXECUTIONS_DATA_PRUNE=true`, `EXECUTIONS_DATA_MAX_AGE=168` | Set at first boot; the default is 336 h, so leaving it alone doubles the retained data. |
| MFA / telemetry / hardening flags | `compose.yaml` n8n block | `N8N_DIAGNOSTICS_ENABLED=false`, `N8N_VERSION_NOTIFICATIONS_ENABLED=false`, `N8N_TEMPLATES_ENABLED=false`, `N8N_BLOCK_ENV_ACCESS_IN_NODE=true`, `N8N_ENFORCE_SETTINGS_FILE_PERMISSIONS=true`. **Not covered by this drill:** MFA enforcement needs a real user account, which a headless drill never creates. |
| Nightly `pg_dump` **and** a restore drill | `scripts/backup.sh`, `scripts/restore_drill.sh` | Backup 8.2 s, restore 30.7 s, verified by digest, ownership, readiness and decryption. The `--no-owner` failure (§6.4) is the reason "the dump exists" is not a backup strategy. |
| `healthz` / metrics / JSON logs | healthchecks, `N8N_METRICS=true`, `N8N_LOG_FORMAT=json` | Readiness is used for ordering (`depends_on: service_healthy`). Two caveats found: readiness turns green before n8n is stable (§6.3), and with JSON logs the *output* of CLI commands like `list:workflow` also arrives as log records, so a filter that drops info-level lines drops the answer. |

## 11. Deprecation warnings emitted by n8n 2.36.7

Recorded verbatim because they will become breakage on a future bump:

* `N8N_RUNNERS_ENABLED` → "Remove this environment variable; it is no longer needed."
* `WEBHOOK_URL` → "Use `N8N_WEBHOOK_URL` instead, which sets the base URL for both test and production webhooks."
* `N8N_RUNNERS_TASK_TIMEOUT` default drops from 300 s to 60 s in a future version.
* `N8N_UNVERIFIED_PACKAGES_ENABLED` default becomes `false`.
* `N8N_COMPRESSION_NODE_MAX_DECOMPRESSED_SIZE_BYTES` 2 GiB → 256 MiB, and
  `N8N_COMPRESSION_NODE_MAX_ZIP_ENTRIES` 5000 → 1000.

Both variables the stack still sets explicitly (`N8N_RUNNERS_ENABLED`, `WEBHOOK_URL`) are
kept for now so the configuration matches the version that was measured.

## 12. Not measured

* No load, concurrency, soak or failure-injection testing. One webhook call is a smoke
  test.
* No ACME / public certificate issuance, no DNS, no renewal.
* No MFA enforcement, no user accounts, no SSO.
* No key rotation drill (`N8N_ENV_FEAT_ENCRYPTION_KEY_ROTATION` was never exercised).
* No restore onto a *different host*, and no test of what happens when the backup itself
  is corrupt — only the `PGDMP` magic-byte check on the way out.
* Nothing about behaviour under memory pressure, and nothing about a second node.
