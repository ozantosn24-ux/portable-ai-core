# Load and soak measurement — 2026-09-07

One recorded run against the **base** compose-drill stack (no `idp` profile). Every number
below came from that run; nothing is carried over from `DRILL-2026-09-06.md`, and nothing is
extrapolated.

> **Codespace ≠ VPS; sayılar mertebe, kapasite modeli değil.**

This measures. It does not tune: no setting in `compose.yaml` was changed, no service was
restarted for the sake of a number, and no result below is presented as a target.

## Exact commands

```bash
# codespace, /workspaces/load
git clone --depth 1 https://github.com/ozantosn24-ux/portable-ai-core.git repo
cd repo/deploy/compose-drill
chmod +x scripts/*.sh
scripts/gen_secrets.sh && scripts/up.sh && scripts/seed.sh

scripts/load.sh probe      # what each endpoint actually answers
scripts/load.sh health     # scenario 1
scripts/load.sh webhook    # scenario 2
scripts/load.sh soak       # scenario 3  (SOAK_SECONDS=600)
scripts/load.sh finish     # docker ps -a + df -h /
```

Each load case is one throwaway container:

```bash
docker run --rm --network drill_default \
  --add-host app.drill.internal:172.19.0.6 --add-host n8n.drill.internal:172.19.0.6 \
  -v scripts/load_client.py:/load_client.py:ro -v ca.crt:/ca.crt:ro \
  drill-load:local \
  python /load_client.py --url https://app.drill.internal/health --method GET \
    --concurrency 100 --duration 30 --cacert /ca.crt --label s1-health-c100
```

Raw outputs (per-case JSON, `docker stats` samples, marker snapshots) were written to
`load-out/` and destroyed with the stack; the numbers below are the whole of what survives.

## Two deviations from the brief, both measured

**1. The webhook is GET, not POST.** `scripts/load.sh probe` asked the live endpoint before
assuming anything:

```
GET  https://app.drill.internal/health          -> 200 15 '{"status":"ok"}'
GET  https://n8n.drill.internal/webhook/drill-ping  -> 200 371 '{"headers":{...
POST https://n8n.drill.internal/webhook/drill-ping  -> 404 110
     '{"code":404,"message":"This webhook is not registered for POST requests.
       Did you mean to make a GET request?"}'
```

`workflows/drill-ping.workflow.json` declares `"httpMethod": "GET"`. Scenario 2 therefore ran
GET. That single POST probe is **the only error line n8n logged in the entire session**.

**2. The client runs on the drill network, on port 443 — not on the host's `127.0.0.1:18443`.**
Caddy is published to loopback only, which a container cannot reach, and the host has no
Python. Running on `drill_default` with `--add-host` keeps the TLS hostname, the SNI, the
certificate chain and the internal-CA verification identical, and takes the host port-forward
(`docker-proxy`) out of the measurement path. Numbers here are therefore *not* comparable to a
future run made through `:18443`.

`err` counts non-2xx **and** client exceptions; both were zero. Postgres CPU peaked at 5.1 /
0.1 / 11.8 %, Caddy at 14.7 / 12.9 / 11.6 %.

**Read this table with two caveats, or do not read it.**

* **The load generator was the largest single CPU consumer.** Its peak was **95.1 % / 95.3 % /
  94.2 %** — roughly a full core of the two available — while the app under test peaked at
  15–43 %. Throughput *falling* from 393 to 298 rps as concurrency rose is at least partly the
  client's own asyncio overhead, not the stack's ceiling. These rps figures are a floor on what
  the stack can do, and they cannot be attributed to the app alone.
* **`/health` does no work.** `src/wozto_ai_reference/api.py:157` returns a static
  `{"status": "ok"}`. Postgres connections never moved off 7–8 during this scenario, which
  confirms it: this measures TLS termination, one proxy hop, and ASGI dispatch. It measures
  nothing about the database, retrieval, or `/query`.

## Scenario 2 — n8n production webhook, 30 s per level

`GET https://n8n.drill.internal/webhook/drill-ping`, client timeout 10 s.

| conc | req | err | rps | p50 | p95 | p99 | max | n8n MiB peak | n8n CPU peak | pg conns |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|:---:|
| 5 | 417 | 0 | 13.69 | 384.43 | 623.59 | 701.53 | 901.28 | 498.3 | 108.3 % | 7 → 8 |
| 20 | 437 | 0 | 14.18 | 1 417.04 | 1 716.15 | 1 832.29 | 1 925.74 | 602.1 | 153.7 % | 8 → 8 |
| 50 | 454 | 0 | 14.11 | 3 545.67 | 3 753.96 | 3 823.30 | 3 882.12 | 829.5 | 169.7 % | 8 → 8 |

**The exact behaviour under saturation, since that was the question.** n8n on 2 vCPU holds a
flat ceiling of ~14 requests per second and absorbs additional concurrency entirely as
latency:

* **No 429s.** Every one of the 1 308 requests returned **200**.
* **No timeouts and no connection errors.** Zero client exceptions; `errors_by_exception` was
  `{}` in all three runs.
* **No load shedding, no queue rejection.** Response time rose in proportion to concurrency at
  constant throughput — `conc ÷ p50` gives 13.0, 14.1, 14.1 req/s, which is the measured rps.
  That is textbook closed-loop queueing, and it means the queue lives in n8n's event loop, not
  in a bounded buffer that could reject.
* **Nothing was dropped.** `execution_entity` grew by exactly 418 / 438 / 455 rows — each run's
  request count plus its one discarded warm-up request. Every accepted request produced one
  persisted execution.
* **Memory tracked concurrency**, 498 → 602 → **829.5 MiB** peak; CPU peaked at 169.7 % of the
  200 % the box has, i.e. n8n alone took ~0.85 of the machine's two cores. n8n-runner stayed at
  12.6–12.8 MiB and **0.0 % CPU** throughout: a NoOp workflow never dispatches a runner task,
  so the external runner was never exercised by this load.

⚠️ The timeout cliff was **not** reached. Max observed latency was 3.88 s against a 10 s client
timeout, so "no timeouts" is a statement about concurrency ≤ 50 at that timeout, not a property
of the stack.

## Scenario 3 — 600 s mixed soak

10 concurrent `/health` and 5 concurrent webhook, running simultaneously, sampled every 30 s.

| stream | req | err | rps | p50 | p95 | p99 | max |
|---|---:|---:|---:|---:|---:|---:|---:|
| health, conc 10 | 130 170 | 0 | 216.93 | 24.75 | 158.25 | 288.55 | 1 038.02 |
| webhook, conc 5 | 4 085 | 0 | 6.80 | 777.68 | 1 213.17 | 1 503.66 | 2 095.82 |

Peaks over 19 samples: n8n **550.0 MiB / 90.9 %**, app 64.4 MiB / 49.9 %, postgres 94.9 MiB /
20.1 %, caddy 63.0 MiB / 12.5 %, n8n-runner 12.6 MiB / 0.0 %; the two load clients together
peaked at 74.4 %, the co-tenant at 17.7 %. Postgres connections stayed in the 7–8 band the
whole time — nowhere near `max_connections=100`.

**The two streams compete.** Webhook throughput fell from ~14 rps alone (scenario 2) to
**6.80 rps** beside the `/health` stream, and `/health` fell from 393 rps alone to 217 rps.
Two vCPU, shared.

**Growth was linear, with no degradation over ten minutes.**

| | before (t0) | after (t+600 s) | delta |
|---|---:|---:|---:|
| `execution_entity` rows | 1 313 | 5 399 | **+4 086** (= 4 085 requests + 1 warm-up) |
| `pg_database_size('drill_n8n')` | 20 215 475 B | 31 774 387 B | **+11 558 912 B (+11.02 MiB)** |
| PGDATA (`du -sb`) | 85 608 984 B | 97 241 624 B | +11 632 640 B (+11.09 MiB) |
| `df /` | 35 % | 36 % | +1 pp |

That is **≈ 2.83 KB of database per execution** for a workflow whose only node is a NoOp.
Row growth was flat at ~226 executions per 30 s sample across all 19 samples; the p50 of the
last minute is not distinguishable from the first.

Sixty seconds after the clients stopped: executions still 5 399 (**no backlog drained
afterwards** — n8n had not been buffering work it hadn't recorded), `drill_n8n` grew a further
57 344 B, connections fell 8 → 7.

**Pruning: nothing pruned, and that is an observation, not a verdict.** Read from the running
container, `EXECUTIONS_DATA_PRUNE=true` and `EXECUTIONS_DATA_MAX_AGE=168` (hours). During and
after the soak: **0** n8n log lines matching `prun|soft.?delete|hard.?delete`, `deletedAt IS
NOT NULL` count **0** at every one of the 22 snapshots, and `execution_entity` never decreased.
A 168-hour age threshold cannot expire anything in a 10-minute window, so this run says only
that **no prune pass was seen here**. It does not show that pruning works, and it does not show
that it is broken. Proving either needs a run with a short `EXECUTIONS_DATA_MAX_AGE` or a
`MAX_COUNT`, which this drill did not do.

## Restarts

`RestartCount` was read for all five drill containers at every one of the **22** marker
snapshots, from `prep` (03:00:13Z) to `final` (03:18:39Z):

```
drill-app-1=0  drill-caddy-1=0  drill-n8n-1=0  drill-n8n-runner-1=0  drill-postgres-1=0
```

**Zero, at every snapshot.** No container was replaced, no OOM kill, and every service was
still `healthy` at the end. Across all eight measured runs — **166 026 requests** — there were
0 non-2xx responses and 0 client exceptions; all eight client stderr files were empty.

## What was NOT measured

* **`/query`.** The one endpoint that touches pgvector, embeddings and the ledger was never
  called. Everything above exercises a static handler and a NoOp workflow. Scenario 1's rps
  says nothing about what this API does when it does its job.
* **TLS handshake cost.** Connections are keep-alive and capped at the concurrency level, so
  handshakes happened during warm-up and were excluded. There is no connections-per-second
  measurement, no session-resumption measurement, and no TLS CPU number.
* **The host-published path.** Nothing went through `127.0.0.1:18443`; `docker-proxy` overhead
  is unmeasured.
* **Multi-node anything.** One host, one Postgres, one n8n main, one runner. No replication, no
  failover, no second main, no queue mode.
* **The runner under load.** A NoOp workflow dispatches no runner task; `n8n-runner` sat at
  0.0 % CPU for the entire session. External-runner throughput is untested.
* **The timeout and error cliff.** No level was pushed until it failed. Where n8n starts
  timing out, shedding, or OOM-ing is unknown — the highest concurrency tried was 50 and it
  still returned 100 % 200s.
* **Sustained load.** Ten minutes is not a soak in any operational sense. Memory was still
  climbing gently at the end; there is no statement here about an hour, a day, or a week.
* **Write load on the app database.** `drill_seed` was read by nothing and written by nothing
  during the load; only n8n wrote to Postgres.
* **Failure injection.** Nothing was killed, throttled, filled, or partitioned.
* **A capacity model.** Deliberately absent. Two vCPU shared with a co-tenant Kubernetes node,
  an overlay filesystem, and a load generator that ate a full core in scenario 1.
  **Codespace ≠ VPS; sayılar mertebe, kapasite modeli değil.**
